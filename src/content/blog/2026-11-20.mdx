## An Apple a Day

I recently made a [post on my LinkedIn](https://lnkd.in/p/gEtWFG6H) that got some attention. It was
a picture of my racked Mac Minis that power my digital life, and a brief overview of what I'm using
them for. I got some asks for a blog post discussing it further, and I'm more than happy to oblige
:)

I started hoarding M4 [Mac Minis](https://www.apple.com/mac-mini/) at the beginning of 2025, back
when the base model Mac Mini would set you back $599. Since then, my homelab's macOS footprint has
grown from one node to six, with a full suite of infrastructure-as-code tooling behind it.

With all of that time passing, I've gotten into a rhythm working with them and I have plenty of
thoughts (`and code!`) to share.

## Wicked Power; Unapologetically Aluminum

Back in 1999, Apple ran [an ad](https://www.youtube.com/watch?v=OoxvLq0dFvw) bragging that the
PowerMac G4 was so powerful it counted as a supercomputer under US export rules, complete with tanks
rolling in to guard it. Makes me wonder how a rack full of Macs working together as an actual
cluster would be classified.

Part of why I went down this path was curiosity about Apple Silicon's performance per watt. A Mac
Mini sips power at idle, runs nearly silent, and still has a Media Engine for video, a GPU that
speaks Metal, and a Neural Engine for CoreML. For a homelab that's on 24/7, and for someone that's
familiar with Apple products, that's a pretty compelling package to put in a rack.

#### The Network

My homelab uses [UniFi](https://ui.com) networking throughout. The Dream Machine Pro handles routing
and doubles as the console for managing everything remotely. The Aggregation switch provides the
10Gbit backbone, and a 24-port switch handles everything that doesn't need the extra bandwidth.

My favorite [Ubiquiti Networks](https://en.wikipedia.org/wiki/Ubiquiti) fun fact is that founder
[Robert Pera](https://en.wikipedia.org/wiki/Robert_Pera) had worked at Apple before starting the
company, so I found it fitting to bring hardware from those two companies together.

#### The Compute

Six Mac Minis live in Sonnet's RackMac Mini enclosures, three to a shelf, each labeled with its
hostname. The Minis are split into two Nomad datacenters:

- **Cosmonautical**
  - The core cluster.
  - Runs Nomad and Consul as server-client combos
  - Hosts everything I self-host, from Postgres to Jellyfin.
- **Jellify**
  - Client-only
  - Primarily runs GitHub Actions runners for [Jellify](https://jellify.app).
    - Xcode, Maestro, simulators, and the Android SDK are all provisioned by Ansible, so a fresh Mac
      goes from unboxed to building and testing apps with a single playbook run.

#### The Storage

Bulk, SSD storage lives on a UNAS Pro 8, which serves NFS shares (music, books, ROMs and so on) to
the whole cluster. A DIY Thunderbolt DAS holds 10 hard drives and is attached directly to
Cassiopeia.

## Software Sells Hardware

Hardware is nothing without the software to leverage it. Running bleeding edge, proprietary hardware
does limit the fun, but as you might imagine there is still plenty of fun to be had.

#### The OS: macOS

The software base is of course, macOS. Linux _does_ support Apple Silicon thanks to the people way
smarter than me working on [Asahi Linux](https://asahilinux.org), but it doesn't support M4 chips -
at least as of the time of this writing.

macOS is very much designed for desktop, and there are a variety of challenges this has given me
despite daily driving a MacBook Pro. Most of them come down to macOS assuming there's a person
sitting in front of the screen, ready to click "Allow".

**[Local Network privacy](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)
is the Achilles' heel.** Since macOS Sequoia, apps need permission to talk to devices on the local
network, and that permission is granted through a GUI prompt. That's great on a laptop, but not on a
headless server. It's tied to the binary's code signature, so every time [Homebrew](https://brew.sh)
upgrades a service like `consul` or `php`, macOS treats the new binary as a stranger and wants a
fresh click. As far as I can tell this can't be scripted either, since the permissions database is
protected by [System Integrity Protection](https://support.apple.com/en-us/102149). It's pretty
frustrating: the daemon logs `no route to host` while `nc` and `ssh` to the exact same IP work just
fine.

To me, this hasn't been a dealbreaker to me, but it means I'm using remote desktop /
[Guacamole](https://guacamole.apache.org) after upgrades to ensure that everything is connecting
properly.

#### The Orchestrator: Nomad

With multiple nodes running, I wanted to have an orchestrator to keep everything in check.

Before the Macs, my homelab ran on a 3-node [Rancher Harvester](https://harvesterhci.io) cluster, so
[Kubernetes](https://kubernetes.io) was what I reached for first. The problem is that Kubernetes is
built and designed with Linux in mind, relying on Linux primitives to do it's job.

I _could_ have run a Linux VM atop macOS to make this work, but that's an extra layer of complexity
every node and it walls workloads off from the things that are fun about Apple Silicon in the first
place: the Media Engine, [Metal](https://developer.apple.com/metal/), and
[CoreML](https://developer.apple.com/machine-learning/core-ml/).

[Nomad](https://www.nomadproject.io) ended up being a perfect fit. It's a single macOS binary, and
its [`raw_exec`](https://developer.hashicorp.com/nomad/docs/job-declare/task-driver/raw_exec) driver
can schedule jobs straight on the host. That means [Jellyfin](https://jellyfin.org) gets hardware
transcoding, [Ollama](https://ollama.com) gets Metal, and CoreML apps get the Neural Engine, all
without any GPU passthrough to setup. Nice.

Nomad is also multi-platform, so the cluster isn't locked into macOS. Linux nodes can join, and if I
ever want a Windows box that can join too.

#### The Container Runtime: Apple Container

Not everything I run ships as a native macOS app, though.

A lot of apps I deploy ship only as an OCI image, and for that we need a way to run the containers.
The obvious choice is Docker, however on macOS that means running a full install of
[Docker Desktop](https://www.docker.com/products/docker-desktop/). [Podman](https://podman.io) is
also an option, and has a [task driver for Nomad](https://github.com/hashicorp/nomad-driver-podman).

I opted instead to write my own task driver for Apple's
[`container`](https://github.com/apple/container) tool, which runs each Linux container in its own
lightweight VM on the
[Virtualization framework](https://developer.apple.com/documentation/virtualization). If you'd like
to try it out for yourself, you can grab the latest release from
[my GitHub repository](https://github.com/anultravioletaurora/nomad-driver-container/releases)

#### The Service Mesh: Consul

Naturally, Nomad pairs nicely with [Consul](https://www.consul.io) for service discovery, health
checks, and key/value storage.

Every service registers itself with Consul, so jobs find each other by name over DNS
(`<service>.service.consul`) instead of hard-coded IPs. It pulls double duty, too: Consul is the
distributed config store that [Patroni](https://github.com/patroni/patroni) uses to handle Postgres
failover, and it's where the Terraform state for my Nomad jobs lives. The three Macs in my
`cosmonautical` datacenter all run as both Nomad and Consul servers.

#### The Management: Ansible

Setting up six Macs by hand was never going to happen, I'm far to lazy for that.

[Ansible](https://www.ansible.com) ended up being a perfect fit for managing this six pack. Running
over SSH and leveraging Python on the target, Ansible needs no additional dependencies outside of
what is preinstalled on every target Mac. There's nothing to bootstrap beyond flipping on Remote
Login.

Since adopting Ansible as my management tool of choice, I've built up quite a collection of
collections. My playbooks have grown into a nice lil family and are
[all published on Ansible Galaxy](https://galaxy.ansible.com/ui/namespaces/cosmonautical/):

- [`cosmonautical.macible`](https://github.com/Cosmonautical-Cloud/Macible): generic macOS roles for
  any Mac, server or workstation. Software Update, Homebrew, Xcode, the Android SDK, NFS mounts,
  container runtimes, etc.
- [`cosmonautical.nomadintosh`](https://github.com/Cosmonautical-Cloud/Nomadintosh): Nomad and
  Consul on macOS, built on top of Macible. Uses Homebrew for the binaries, and bootstraps
  LaunchAgents to keep them running.
- [`cosmonautical.nomaduntu`](https://github.com/Cosmonautical-Cloud/Nomaduntu): the Ubuntu
  counterpart, using HashiCorp's apt repo and systemd.
- [`cosmonautical.nomadable`](https://github.com/Cosmonautical-Cloud/Nomadable): the parent
  playbook. It routes each host to Nomadintosh or Nomaduntu based on its OS, so a mixed macOS and
  Ubuntu cluster deploys in a single run.

The [Nomad jobs](https://github.com/Jellify-Music/Nomad-Jobs) themselves are defined in
[Terraform](https://www.terraform.io), and both the Ansible playbooks and Terraform solutions get
run by [Semaphore](https://semaphoreui.com), which (of course) runs as a Nomad job on the very
cluster it deploys to.

#### Apple + IBM sounds familar...

If you're keeping track: Nomad, Consul, and Terraform come from HashiCorp, which IBM acquired in
2025, and Ansible comes from Red Hat, which IBM acquired back in 2019. So my homelab is
_technically_ Apple hardware running IBM software.

Just missing Motorola in the mix and it's like [AIM](https://en.wikipedia.org/wiki/AIM_alliance)
never dissolved.

## Roll out the barrels

The jobs I run on the Mac Rack Mini Pro can be broken up into tiers, based on their criticality of
the application.

- Tier 1 (Core Infrastructure):
  - [Postgres](https://www.postgresql.org) (Patroni, using Consul as its DCS)
    - A separate Nomad job takes a `pg_dumpall` every 6 hours
  - [Redis](https://redis.io) +
    [Sentinel](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)
  - [SeaweedFS](https://github.com/seaweedfs/seaweedfs) (3 masters, 3 volume servers, a filer, NFS
    backup)
  - [Traefik](https://traefik.io) + [Fail2ban](https://github.com/fail2ban/fail2ban)
  - [OpenLDAP](https://www.openldap.org) + [Keycloak](https://www.keycloak.org)
  - Semaphore
    - Runs the Ansible and Terraform that deploy everything else, including itself
- Tier 2 (Critical Applications):
  - [Nextcloud](https://nextcloud.com)
    - Primary app is deployed as a Nomad service
    - Nomad batch jobs are deployed for Nextcloud tasks to run on schedule
      - Nextcloud's cron
      - preview generation
      - NFS share scans
      - S3 backups to Backblaze
  - Jellyfin
    - A native `.app` that uses Apple MediaToolbox for
      [hardware accelerated transcoding](https://jellyfin.org/docs/general/post-install/transcoding/hardware-acceleration/)
    - [Dispatcharr](https://github.com/Dispatcharr/Dispatcharr) acts as an HDHomeRun tuner for Live
      TV
  - [AudioMuse-AI](https://github.com/NeptuneHub/AudioMuse-AI)
    - a native `.app` for music sonic analysis, leveraging CoreML
  - Ollama + [Open WebUI](https://openwebui.com)
- Tier 3 (Secondary Applications)
  - [RomM](https://github.com/rommapp/romm)
  - Guacamole
  - [Seerr](https://github.com/seerr-team/seerr) for media requests
  - GitHub Actions runners for Jellify
    - A Nomad `system` job puts one ephemeral runner on every node tagged as a runner. Each runner
      takes exactly one job, wipes its work folder, and registers a fresh replacement, so no build
      ever sees the last one's leftovers.
    - **[Maestro](https://maestro.mobile.dev) end-to-end tests** are the headline act.
      - Every PR, plus a nightly run, builds a release copy of the app and drives it through the
        full UI flow on _both_ an iOS Simulator and an Android emulator: setup and login, home,
        quick actions, library, search, discover, settings, and the player and queue.
      - The same flows run on both platforms, with small helper subflows papering over the
        differences (iOS has no back button, for one).
      - Screenshots, logs, and the UI hierarchy get uploaded as artifacts, and the result gets
        posted to Discord.
      - These run as `raw_exec` straight on macOS, using the Xcode, simulators, and Android SDK that
        Ansible provisions.
    - Everything else that doesn't need a Mac lands on x64 Linux runners in the same job:
      - Jest unit tests on every branch push
      - JS bundle and Android APK builds on PRs
      - Publishing OTA updates, and cleaning up the per-PR OTA branches once a PR closes
    - Fork PRs get GitHub's hosted runners instead, so fork code never runs on my hardware.

Some jobs are `raw_exec`, running on bare macOS (Jellyfin, Postgres/Patroni, Nextcloud's php-fpm,
AudioMuse), others are Linux containers through Apple `container` via my
[`nomad-driver-container`](https://github.com/anultravioletaurora/nomad-driver-container) plugin.

## Standardized Operationing Prodecures

With vulnerabilities landing faster than ever, I've had plenty of practice running through patching
procedures. Patches go in one of two ways: Homebrew via Ansible, or Nomad jobs via Semaphore.

### Homebrewed

Homebrew upgrades get deployed by rerunning the Nomadintosh playbook. Every run upgrades Nomad,
Consul, and the rest of the Homebrew packages in my inventory to their latest versions, so patching
a host is as simple as running the playbook again.

Upgrading is the easy part. As I mentioned earlier, Homebrew swaps the binary, not the process, so
the playbook also handles the restarts:

- **Nomad and Consul** restart one host at a time, and the playbook waits for the agent and the
  cluster to report healthy before moving on to the next one. A run that upgrades every server never
  takes more than one of them out of quorum.
- **Nomad jobs** running directly on macOS (`raw_exec`) get restarted afterwards, again one at a
  time. They'd otherwise keep running the old binaries, under an executor started by the old `nomad`
  binary that Homebrew has since deleted, which is how my Postgres replicas once ended up ~23 GB
  behind for days without a peep.

The one step that can't be automated is the Local Network prompt. After an upgrade, I hop onto each
Mac via Guacamole and click "Allow" for the freshly signed binaries.

### Nomad Life

Version bumps for Nomad jobs come from [Renovate](https://github.com/renovatebot/renovate), which
opens a PR against my Terraform whenever a new release of an app ships. Once I merge it to `main`,
Semaphore runs `terraform plan` and then holds the change for my approval before `terraform apply`
rolls it out to the cluster. GitOps FTW.
